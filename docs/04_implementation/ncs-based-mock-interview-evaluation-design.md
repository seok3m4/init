# NCS 기반 모의면접 평가체계 설계

## 1. 목적

지원자 모의면접에 NCS(국가직무능력표준)를 적용해, 공식 능력단위 정보에서 도출한 행동 포인트와 실제 답변 근거를 바탕으로 객관적이고 정량적인 피드백을 제공한다.

이 기능은 합격·불합격을 예측하지 않는다. 제한된 사용자 표본으로 만든 상대평가 대신 NCS 정보에 근거한 공통 행동 루브릭 평가와 동일 사용자의 재도전 전후 비교를 제공한다.

직무·NCS 전문가의 수동 검수를 필수 운영 단계로 두지 않는다. 대신 공식 데이터 추적성, 규칙 검증, 가상 답변 블라인드 채점, 변형 테스트로 시스템의 일관성과 안전성을 자동 검증한다. 이 검증은 산업현장 타당성이나 채용 성과 예측력을 증명하지 않는다.

## 2. 적용 범위

- 대상은 관리자 없는 지원자 단독 모의면접 흐름이다.
- 평가는 `직업기초능력 + 직무수행능력` 혼합형으로 구성한다.
- 직무수행능력 카탈로그는 NCS 정보통신 대분류의 전체 능력단위를 대상으로 한다.
- 채용공고 또는 JD를 분석해 NCS 세분류와 능력단위를 추천한다.
- 추천 결과는 지원자가 확인·선택한 뒤에만 질문 생성과 평가에 사용한다.
- 표정, 시선, 말속도, 억양 등 비언어 정보는 NCS 총점에서 제외하고 별도 전달 방식 코칭에만 사용한다.

## 3. 설계 원칙

1. 점수마다 NCS 능력단위·요소, AI 생성 행동 포인트, 실제 발화 근거, 판정 이유를 연결한다.
2. AI는 근거 추출과 루브릭 판정을 담당하고, 점수 환산과 가중합은 일반 코드로 계산한다.
3. 근거가 없으면 낮은 역량으로 추정하지 않고 `평가 불충분`으로 처리한다.
4. 질문되지 않은 역량과 면접으로 관찰할 수 없는 행동 포인트는 채점하지 않는다.
5. NCS와 루브릭 버전을 세션에 고정해 재평가 가능성을 보장한다.
6. 민감하거나 직무와 무관한 속성은 평가 입력과 총점에서 제외한다.
7. 공식 NCS 데이터와 서비스가 AI로 생성한 면접용 평가 프로필을 구분해 표시한다.
8. 자동 검증 통과는 전문가 검증이나 NCS 인증을 의미하지 않는다.

## 4. 사용자 설정 흐름

1. 지원자가 채용공고 또는 JD를 선택한다.
2. 시스템이 직무, 주요 업무, 요구 기술을 추출한다.
3. 시스템이 RDS의 정보통신 NCS 카탈로그에서 세분류와 관련 능력단위를 최대 5개 추천한다.
4. 각 추천에는 능력단위 코드·명칭·수준, JD 연결 문구, 추천 이유, 신뢰도를 표시한다.
5. 지원자는 추천된 직무수행능력 중 3~5개를 최종 선택한다.
6. 지원자는 NCS 직업기초능력 중 3~5개를 직접 선택한다.
7. 지원자는 직업기초능력과 직무수행능력의 비중을 10% 단위로 설정한다.
8. 혼합형을 유지하기 위해 각 영역의 최소 비중은 10%로 제한한다.
9. 선택을 확정하면 질문·행동 포인트 연결표와 평가 루브릭을 생성한다.
10. 확정한 NCS 버전, 능력단위·요소, 행동 포인트, 선택 영역, 비중을 면접 세션의 평가 스냅샷으로 고정한다.

최소 10%와 10% 단위는 NCS 공식 배점 기준이 아니라 혼합형을 유지하고 사용자 선택을 단순화하기 위한 제품 정책이다.

## 5. NCS 매핑 정책

공공데이터포털의 NCS 기준정보 API를 통해 정보통신 대분류의 분류, 능력단위, 능력단위요소를 AWS RDS PostgreSQL에 적재한다. 실제 제공 필드 범위 안에서 능력단위 코드·명칭·수준·정의·요소를 평가 프로필의 공식 원천으로 사용한다.

### 5.1 클라우드 동기화

- 최초 배포 시 관리용 스크립트 또는 ECS 일회성 Task로 데이터를 적재한다.
- 이후 갱신이 필요할 때 같은 Task를 수동 실행한다.
- 일반 API 요청과 면접 중에는 공공데이터 API를 직접 호출하지 않는다.
- API 인증키는 ECS Secret 또는 AWS Secrets Manager로 주입하고 저장소에 커밋하지 않는다.
- NCS 코드와 버전을 기준으로 upsert하고 중복 저장을 막는다.
- 동기화가 실패하면 기존 RDS 카탈로그를 유지하고 실패 로그를 남긴다.
- 자동 정기 동기화와 EventBridge 스케줄은 MVP 범위에서 제외한다.

### 5.2 로컬 개발과 클라우드 운영

같은 애플리케이션 코드와 데이터 계약을 로컬 개발 환경과 AWS 운영 환경에서 사용한다. 환경별 차이는 연결 주소와 비밀값 주입 방식으로 제한한다.

| 구성요소 | 로컬 개발·최초 테스트 | AWS 운영 |
| --- | --- | --- |
| PostgreSQL | `infra/local/docker-compose.yml`의 로컬 PostgreSQL | Amazon RDS PostgreSQL |
| SQS/S3 | LocalStack의 SQS·S3 | AWS SQS·S3 |
| API·worker | 로컬 Node.js 프로세스 또는 Docker 컨테이너 | ECS Service·Task |
| NCS 동기화 | 개발자 명령으로 동일한 동기화 스크립트 실행 | ECS 일회성 Task 실행 |
| 비밀값 | 커밋하지 않은 로컬 `.env` | ECS Secret 또는 AWS Secrets Manager |

로컬 최초 테스트는 다음 흐름을 지원한다.

```text
로컬 PostgreSQL·LocalStack 실행
→ NCS 동기화 스크립트 실행
→ 정보통신 카탈로그 적재 확인
→ API와 worker 실행
→ 평가 프로필 생성·자동 검증
→ 모의면접 질문 생성·채점·리포트 확인
```

동기화 스크립트와 worker는 `DATABASE_URL`, `AWS_ENDPOINT_URL`, `SQS_QUEUE_URL` 등 환경변수로 실행 대상을 전환한다. 로컬 전용 평가 로직이나 클라우드 전용 데이터 형식을 만들지 않는다.

### 5.3 검색과 추천

- JD와 NCS의 관련성은 자동 추천하되 자동 확정하지 않는다.
- 복잡한 별도 학습 모델 대신 JD 키워드와 NCS 명칭·정의·요소의 텍스트 유사도로 후보를 정렬한다.
- JD와 관련성이 낮은 추천은 경고하되 지원자의 선택을 막지 않는다.
- 장비 조작, 실물 제작, 현장 실습 등 면접 답변만으로 검증할 수 없는 능력단위·요소는 `면접 평가 부적합`으로 제외한다.
- NCS 원본이 개정되어도 기존 면접의 평가 스냅샷과 결과는 변경하지 않는다.
- 낮은 매핑 신뢰도는 사용자에게 표시하고, 확정적인 직무 일치 표현을 사용하지 않는다.

### 5.4 면접용 평가 프로필

정보통신 전체 능력단위에 전용 5단계 루브릭을 사람이 작성하지 않는다. 사용자가 선택한 능력단위에 대해서만 AI가 다음 서비스 생성 데이터를 만든다.

- 면접으로 확인할 행동 포인트 2~3개
- 본 질문 1~2개와 선택적 꼬리질문
- 답변에서 확인할 근거
- 면접 평가 부적합 여부와 사유

평가 프로필은 NCS 코드·버전, 프롬프트 버전, 모델 버전을 키로 RDS에 캐시한다. 공식 NCS 문구와 AI 생성 문구를 데이터와 화면에서 구분한다.

## 6. 질문 설계

면접 시작 전에 `선택 역량 → 행동 포인트 → 질문` 연결표를 만든다.

- 선택한 각 역량에는 최소 2회의 독립적인 평가 기회를 배정한다.
- 하나의 질문으로 직업기초능력과 직무수행능력을 함께 관찰할 수 있다.
- 같은 답변을 여러 항목에 사용할 때는 항목별 근거와 판정 이유를 각각 생성한다.
- 단순 지식 확인보다 실제 상황, 본인의 과제, 행동, 결과, 성찰을 확인하는 경험 질문을 우선한다.
- 답변이 추상적이면 빠진 근거를 확인하는 꼬리질문을 1회 생성할 수 있다.
- 시작 전에 예상 질문 수와 예상 시간을 표시한다.
- 3~5개씩 선택한 일반적인 세션은 본 질문과 꼬리질문을 합해 약 8~12개를 목표로 하되, 고정 개수로 강제하지 않는다.

질문 세트 확정 전 다음을 검증한다.

- 선택한 모든 역량에 평가 기회가 있는가
- 면접 평가 부적합 행동 포인트가 포함되지 않았는가
- 특정 역량에 질문이 과도하게 몰리지 않았는가
- 유도 질문이나 정답을 암시하는 표현이 없는가

## 7. 공통 5단계 행동 루브릭

능력단위마다 서로 다른 전용 단계 기준을 생성하지 않고, 모든 정보통신 능력단위에 같은 공통 기준을 적용한다. AI가 생성한 행동 포인트는 무엇을 확인할지 정하고, 공통 루브릭은 확인된 답변 근거의 수준을 판정한다.

| 단계 | 환산점수 | 공통 판정 기준 |
| ---: | ---: | --- |
| 5 | 100 | 구체적인 수행 경험, 선택 근거, 결과와 개선점이 모두 확인된다. |
| 4 | 85 | 구체적인 수행 경험과 결과가 확인된다. |
| 3 | 70 | 관련 지식과 경험은 있으나 본인의 행동 또는 결과가 부족하다. |
| 2 | 50 | 개념 설명은 있으나 실제 수행 근거가 부족하다. |
| 1 | 25 | 관련 답변은 있으나 능력 보유를 뒷받침하지 못한다. |
| 평가 불충분 | 제외 | 질문되지 않았거나 답변 자료가 부족해 판정할 수 없다. |

`근거 없음`은 1단계가 아니다. 1단계는 평가할 수 있는 관련 발화가 있으나 행동 포인트 충족 근거가 부족한 경우에만 사용한다.

각 판정은 다음 정보를 포함한다.

- 질문 ID와 답변 ID
- NCS 버전, 능력단위 코드, 능력단위요소와 AI 생성 행동 포인트
- 답변에서 추출한 근거 문장
- 루브릭 단계와 환산점수
- 판정 이유
- 판정 신뢰도

## 8. 점수 계산

한 능력에 여러 행동 포인트가 있으면 평가 가능한 행동 포인트 점수의 산술평균으로 능력 점수를 계산한다. 선택한 능력들은 기본적으로 동일 비중을 가진다.

```text
직업기초능력 점수
= 평가 가능한 선택 직업기초능력 점수의 평균

직무수행능력 점수
= 평가 가능한 선택 직무수행능력 점수의 평균

맞춤 총점
= 직업기초능력 점수 × 사용자 선택 비중
+ 직무수행능력 점수 × 사용자 선택 비중
```

최종 화면에는 반올림한 정수 점수를 표시하되 내부 계산값은 소수점 정밀도를 유지한다.

일부 행동 포인트가 평가 불충분이면 같은 능력 안의 평가 가능한 행동 포인트로 정규화한다. 어느 한 대영역 전체에 평가 가능한 근거가 없으면 사용자가 정한 영역 비중을 다른 영역에 재배분하지 않고 총점을 `평가 근거 부족`으로 표시한다.

맞춤 총점만 사용자에게 표시한다. 다른 사용자 비교용 표준 총점은 계산하거나 노출하지 않는다. 총점 옆에는 사용자가 선택한 비중을 항상 표시한다.

## 9. 결과 리포트

결과는 다음 순서로 제공한다.

1. 맞춤 총점과 선택 비중
2. 강점 2개와 우선 개선점 2개
3. 직업기초능력과 직무수행능력의 능력별 점수
4. 행동 포인트별 실제 발화 근거와 누락된 근거
5. 상황·과제·행동·결과·성찰 기준의 답변 완성도
6. 지식·기술·태도별 진단
7. 근거 품질 진단
8. 다음 답변에서 실행할 구체적인 개선 방법
9. 동일 질문 재도전
10. 이전 면접 대비 변화

근거 품질은 직무 역량과 분리해 다음 항목으로 진단한다.

- 구체성: 실제 상황과 행동이 명확한가
- 관련성: 질문과 행동 포인트에 직접 답했는가
- 검증 가능성: 기간, 수치, 역할, 결과가 제시됐는가
- 주도성: 팀 성과와 본인의 행동이 구분되는가
- 일관성: 본 질문과 꼬리질문의 내용이 모순되지 않는가

근거 품질은 답변 전달의 완성도를 설명하는 보조 지표이며 NCS 역량 점수를 임의로 가감하지 않는다.

## 10. 평가 신뢰도

총점과 능력별 판정에는 신뢰도를 함께 표시한다.

| 신뢰도 | 기준 |
| --- | --- |
| 높음 | 복수 질문에서 일관된 구체적 근거를 확보했다. |
| 보통 | 한 질문에서 구체적 근거를 확보했다. |
| 낮음 | 간접적이거나 불완전한 근거만 확보했다. |
| 평가 불충분 | 채점 가능한 근거가 없다. |

## 11. 비교와 예측 정책

- 타 사용자 백분위와 합격·불합격 확률은 이번 범위에서 제공하지 않는다.
- 제한된 표본에서는 동일 사용자의 재도전 전후 변화만 비교한다.
- 실제 채용 결과, 동일 직무·경력 조건, 기업별 기준과 충분한 표본이 축적되기 전에는 합격 가능성이라는 표현을 사용하지 않는다.
- 향후 예측 기능은 별도 모델, 데이터 동의, 개인정보·편향 검토, 확률 보정과 검증을 거치는 독립 기능으로 설계한다.

## 12. 비언어 코칭과 공정성

- 표정, 시선, 말속도, 목소리 톤, 억양, 말투는 NCS 총점에 반영하지 않는다.
- 비언어 정보는 사용자가 동의한 경우에만 별도 `전달 방식 코칭`으로 제공한다.
- 성별, 나이, 출신 학교, 출신지, 외모, 장애 여부, 건강 상태 등 민감하거나 직무와 무관한 속성을 평가하거나 추정하지 않는다.
- 답변 transcript와 확정된 평가 스냅샷에 없는 사실을 추정하지 않는다.
- 결과는 합격·불합격이나 채용 적합·부적합이 아니라 선택 역량의 모의면접 수행 수준으로 설명한다.

## 13. 처리 구조

```text
배포 또는 수동 ECS Task로 정보통신 NCS 카탈로그 동기화
→ JD 분석
→ NCS 직무·능력단위 추천
→ 사용자 선택 및 가중치 확정
→ 선택 능력단위의 평가 프로필 조회 또는 생성
→ 자동 검증 후 ACTIVE 프로필 캐시
→ 평가 스냅샷과 질문·행동 포인트 연결표 생성
→ 면접 답변 수집 및 STT
→ 답변 근거 추출
→ 행동 포인트별 공통 5단계 판정
→ 결정론적 점수 계산
→ 개선 피드백 생성
→ 가드레일 검증
→ 결과 저장
```

구성요소의 책임은 다음과 같다.

- NCS 카탈로그: 공식 API가 제공하는 NCS 버전, 분류, 능력단위, 정의, 능력단위요소 관리
- NCS 동기화 Task: 공공데이터 API의 정보통신 데이터를 RDS에 적재
- 매핑 엔진: JD와 NCS 능력단위의 키워드·텍스트 유사도 추천
- 평가 프로필 생성기: 선택 능력단위의 행동 포인트, 질문, 근거 기준 생성
- 자동 검증기: 규칙, 가상 답변, 블라인드 채점, 변형 테스트 실행
- 면접 설계기: 선택 역량의 평가 기회를 포함한 질문 구성
- 근거 추출기: 답변에서 평가 가능한 발화 추출
- 루브릭 평가기: 근거와 고정된 5단계 기준 비교
- 점수 계산기: 환산점수와 가중합을 결정론적으로 계산
- 피드백 생성기: 누락 근거, 답변 완성도, 개선 행동 생성
- 검증기: 근거 없는 점수, 잘못된 합계, 금지 표현 차단

장기 AI 처리는 기존 `ai_process_logs → SQS → worker → ai_guardrail_logs` 흐름을 사용한다. 가드레일이 `PASS` 또는 `REGENERATED`가 되기 전에는 최종 평가 결과를 저장하지 않는다.

평가 프로필은 정보통신 전체를 사전 생성하지 않는다. 사용자가 처음 선택한 능력단위만 SQS worker에서 생성·검증하고, 같은 NCS 코드·버전·프롬프트·모델 조합은 캐시를 재사용한다.

## 14. 자동 평가 프로필 검증

평가 프로필 생성부터 활성화까지 사용자 테스트 외에는 사람의 승인을 요구하지 않는다.

```text
평가 프로필 생성
→ 규칙 기반 검증
→ 수준별 가상 답변 생성
→ 목표 단계를 숨긴 블라인드 재채점
→ 단계 순서·근거 연결 검증
→ 무관 속성 및 핵심 근거 변형 테스트
→ 통과 시 ACTIVE, 실패 시 최대 2회 재생성
```

### 14.1 규칙 검증

- 행동 포인트가 2~3개인지 확인한다.
- 각 행동 포인트가 공식 NCS 정의 또는 능력단위요소와 연결되는지 확인한다.
- 면접 답변으로 관찰 가능한 표현인지 확인한다.
- 금지 속성과 모호한 인상 평가가 없는지 확인한다.
- 구조화된 JSON 출력이 계약과 일치하는지 확인한다.

### 14.2 가상 답변 블라인드 채점

생성기가 우수, 보통, 부족, 질문과 무관, 답변 없음, 그럴듯하지만 수행 근거가 없는 답변을 만든다. 평가기에는 생성 목표를 전달하지 않는다.

자동 통과 조건은 다음과 같다.

- 우수 점수 > 보통 점수 > 부족 점수 순서가 유지된다.
- 질문과 무관한 답변은 1단계 또는 평가 불충분이다.
- 답변 없음은 평가 불충분이다.
- 모든 점수에 실제 가상 답변의 근거가 연결된다.
- 답변에 없는 사실이 판정 근거로 생성되지 않는다.

### 14.3 변형 테스트

- 이름, 성별 암시 표현, 학교명, 문장 순서, 존댓말 여부만 바꾼 답변의 점수는 허용 범위 안에서 유지되어야 한다.
- 문제 원인, 본인의 행동, 결과 등 핵심 근거를 제거하면 점수가 같거나 높아져서는 안 된다.

### 14.4 상태와 실패 정책

평가 프로필은 `GENERATING`, `VALIDATING`, `ACTIVE`, `RETRY_REQUIRED`, `UNAVAILABLE` 상태를 가진다. 최대 2회 재생성 후에도 실패하면 `UNAVAILABLE`로 두고 사용자에게 현재 자동 평가를 준비할 수 없다고 안내한다.

## 15. 실패와 예외 처리

- NCS 동기화 실패: 기존 카탈로그를 유지하고 관리 로그에 실패 사유를 기록한다.
- STT 실패: 답변 품질을 0점으로 추정하지 않고 `평가 불충분`과 재녹음 안내를 표시한다.
- NCS 매핑 실패: 자동 선택하지 않고 직접 직무 탐색 또는 재시도를 제공한다.
- 평가 프로필 생성·검증 실패: 최대 2회 재시도 후 해당 능력단위를 일시적으로 사용할 수 없다고 표시한다.
- 질문 커버리지 실패: 면접을 시작하지 않고 질문 세트를 재생성한다.
- 근거 추출 실패: 해당 행동 포인트를 평가 불충분으로 처리하고 AI 작업 실패 사유를 기록한다.
- 가드레일 차단: 결과를 최종 저장하지 않고 안전한 재생성 또는 재시도를 제공한다.
- 중복 worker 처리: `processLogId`를 멱등성 키로 사용해 중복 평가 저장을 막는다.
- NCS 원본 변경: 진행 중이거나 완료된 세션의 평가 스냅샷을 변경하지 않는다.

## 16. 검증 전략과 수용 기준

### 계산 및 계약 테스트

- 선택 비중 합계가 100이고 각 영역이 10% 이상인지 검증한다.
- 5단계 환산점수와 맞춤 총점 계산을 경계값까지 검증한다.
- 일부 행동 포인트의 평가 불충분 정규화가 정확한지 검증한다.
- 한 대영역 전체가 평가 불충분이면 총점을 만들지 않는지 검증한다.
- AI가 반환한 총점 값을 신뢰하지 않고 서버 계산값만 저장하는지 검증한다.

### 자동 평가 품질 테스트

- 규칙 검증, 가상 답변 블라인드 채점, 변형 테스트가 모두 통과해야 평가 프로필을 활성화한다.
- 모든 점수에 실제 답변 근거와 NCS 출처가 연결되는지 검증한다.
- 같은 입력의 반복 평가가 ±1단계를 넘지 않는지 측정한다.
- 한 답변을 여러 기준에 사용할 때 항목별 판정 이유가 독립적인지 검증한다.
- 질문 세트가 모든 선택 역량에 최소 2회의 평가 기회를 제공하는지 검증한다.
- 재도전 비교가 동일한 평가 스냅샷을 사용하는지 검증한다.

### 공정성 및 가드레일 테스트

- 이름, 성별, 나이, 학교, 출신지, 외모 관련 문구를 바꿔도 점수가 달라지지 않는 대조 테스트를 수행한다.
- 표정, 시선, 억양 등 비언어 지표가 NCS 총점 계산 입력에 포함되지 않는지 검증한다.
- 합격·불합격, 채용 가능성, 채용 적합성 단정 표현을 차단한다.
- transcript, NCS 원천 정보, 행동 포인트에 없는 사실을 근거로 저장하지 않는다.

수용 기준은 계산 테스트 전부 통과, 근거 없는 점수 0건, 금지 속성의 점수 입력 0건, 가상 답변의 단계 순서 위반 0건이다. 실제 사용자 5~10명의 사용성 테스트는 자동 검증과 별도로 진행한다.

이 검증 결과는 시스템 내부 일관성과 안전성에 대한 증거다. NCS 전문가 검증, NCS 인증, 산업현장 타당성, 실제 채용 성과와의 상관관계를 주장하지 않는다.

## 17. 기존 시스템과의 관계

현재 서비스의 `evaluation_criteria`, `question_bank`, `evaluation_reports`, `report_scores`, `report_evidences`와 5단계 루브릭·100점 가중합 구조를 확장한다. 구현 시 다음 계약 변경이 예상되므로 코드보다 문서를 먼저 갱신한다.

- NCS 카탈로그와 버전 관리 데이터 모델
- NCS 동기화 실행과 실패 이력
- AI 생성 평가 프로필, 자동 검증 상태와 캐시 키
- 세션별 평가 스냅샷과 사용자 선택 비중
- 질문과 행동 포인트의 다대다 연결
- 행동 포인트별 판정, 신뢰도, 평가 불충분 상태
- 재도전 비교를 위한 기준 세션 연결
- 모의면접 결과 리포트 응답 계약

`question_bank`와 `evaluation_criteria`는 C/E 공동 검토가 필요하고, `interview_sessions`, `interview_session_questions`, `interview_answers` 변경은 D 검토가 필요하다. 리포트와 AI 처리 변경은 E 검토가 필요하다.

## 18. 이번 설계의 비범위

- 기업 채용면접의 관리자 평가 설정
- 합격·불합격 또는 채용 통과 확률 예측
- 타 사용자 백분위와 순위
- 비언어 정보의 NCS 점수 반영
- 현장 실습이나 작업 결과물 평가
- NCS 원문 전체의 수동 관리 UI
- NCS 전문가 수동 승인 절차
- NCS 인증 또는 산업현장 타당성 보장
- EventBridge 기반 정기 NCS 동기화

## 19. 구현 주체와 완성품 비교 방식

이 문서를 구현하는 현재 워크트리는 한 명의 구현자가 M0 계약부터 평가기, 사용자 route, STT 연동, 결과 리포트까지 하나의 완성품으로 책임진다.

M1에서 여러 평가 전략을 병렬 실행하는 것은 팀원별 기능 분담이 아니다. 다중 Codex 에이전트가 충돌하지 않는 전략 디렉터리에서 후보 평가기를 동시에 만들고, 단일 구현자가 결과를 검증해 하나를 채택하기 위한 내부 실험이다.

다른 팀원은 이 구현의 일부 모듈을 맡지 않는다. 각 팀원은 동일한 설계 문서를 입력으로 사용하되 질문 생성부터 답변 평가와 결과 표시까지 독립적인 완성품 하나를 만든다. 비교와 채택은 부분 코드나 개별 전략이 아니라 다음 공통 시나리오를 실행할 수 있는 완성품 단위로 수행한다.

```text
직무 선택
→ 면접 시작
→ 질문 텍스트 생성
→ 답변 입력 또는 STT transcript 수집
→ 행동 포인트별 평가
→ 근거와 점수가 포함된 결과 표시
```

## 20. 실행 마일스톤

| 단계 | 목표 | 종료 조건 |
| --- | --- | --- |
| M0 | 평가 계약과 기준선 고정 | JSON 계약, 48개 fixture, 실제 baseline 결과, hard gate 검증 완료 |
| M1 | 후보 평가기 병렬 구현 | 네 전략이 각각 실행 가능하고 48개 case를 5회 평가한 결과를 생성 |
| M2 | 평가기 비교와 채택 | hard gate를 통과한 후보를 정확도, 근거, 안정성, 비용 순으로 비교해 하나를 채택 |
| M3 | 제품용 평가 서비스 연결 | 채택 평가기를 API 또는 worker 경계에 연결하고 질문·답변·결과 계약을 고정 |
| M4 | 텍스트 수직 기능 완성 | 직무 선택부터 질문 생성, 텍스트 답변 입력, 평가 결과 표시까지 route 하나에서 동작 |
| M5 | 화상면접 통합 | 녹화·실시간 STT transcript를 평가 입력으로 사용하고 최종 결과를 리포트로 제공 |

M1과 M2는 후보 결과가 도착하는 즉시 비교할 수 있으므로 병렬 진행한다. M3 이후에는 채택된 평가기 하나만 제품 경로로 옮긴다.

### 현재 구현 상태 (2026-07-13)

- M0~M4는 계약, 평가기 비교, 제품 API, 텍스트 route와 실제 DB/worker 왕복까지 구현됐다.
- M5의 `STORED_ANSWER → NCS 평가 → immutable revision → 모의면접 리포트` 코드 경로와 자동 테스트는 구현됐다.
- 선택 직무별 합성 평가 프로필과 세션 질문별 immutable snapshot을 추가해, 프로필 변경과 API 재시작이 진행 중 세션을 바꾸지 않게 했다.
- 실제 화상면접 표본을 이용한 STT calibration과 사용자 검증은 데이터가 생긴 뒤 수행해야 하며 자동 테스트 완료와 구분한다.

## 21. 현재 마일스톤 최종 데모

현재 구현 마일스톤의 사용자 수용 기준에는 `/candidate/mock-interview/ncs-evaluation` route를 포함한다. 첫 수직 기능은 카메라나 외부 STT 가용성에 의존하지 않는 텍스트 입력 방식으로 완성한다.

1. 지원자가 직무를 선택한다.
2. 시작 버튼을 누르면 선택 직무에 맞는 질문 텍스트와 행동 포인트가 생성된다.
3. 지원자가 textarea에 답변을 입력하고 평가를 요청한다.
4. 화면에 행동 포인트별 상태, 1~5단계, 환산점수, transcript 근거 인용, 판정 이유를 표시한다.
5. 근거가 부족하면 부족한 행동 포인트와 꼬리질문을 표시한다.
6. 민감 속성과 비언어 정보는 NCS 점수에 사용하지 않는다.

route 파일은 기존 Next.js 규칙대로 얇게 유지하고 실제 화면과 상태는 feature 모듈에 둔다. 이후 화상면접 통합에서는 새 녹화·리포트 체계를 만들지 않고 다음 기존 경계를 재사용한다.

- 시작 route: `frontend/src/app/candidate/mock-interview/start/page.tsx`
- 면접 runtime route: `frontend/src/app/candidate/mock-interviews/[sessionId]/page.tsx`
- 실시간 STT client: `frontend/src/features/candidate-application-interview/realtime-stt-relay.ts`
- 실시간 STT relay server: `backend/api/src/modules/interview/realtime-stt-relay.server.ts`
- 비동기 STT provider: `backend/worker/src/stt-provider.ts`
- 모의면접 리포트 route: `frontend/src/app/candidate/mock-interview/reports/[reportId]/page.tsx`
- 리포트 API와 worker: `backend/api/src/modules/report`, `backend/worker/src/mock-ai-task.handler.ts`

텍스트 route에서 검증한 평가 입력은 향후 `textarea 값` 대신 `STT transcript`를 받도록 교체한다. 평가 결과는 기존 `evaluation_reports`, `report_scores`, `report_evidences`와 가드레일 흐름을 통해 최종 리포트에 합류한다.
